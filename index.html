01SELECT Essentials

Read this section as a pipeline: filter rows → pick columns → sort → limit. Almost every interview question starts here, and the traps start here too — mostly around NULL.

-- The everyday pipeline
SELECT customer_id, name, country, signup_date
FROM customers
WHERE country IN ('US', 'CA')          -- membership list
  AND signup_date >= '2024-01-01'      -- comparison
  AND name LIKE 'A%'                   -- pattern: starts with A
  AND deleted_at IS NULL               -- NULL check (never "= NULL")
ORDER BY signup_date DESC, name ASC    -- multi-key sort
LIMIT 20;                              -- PG/MySQL · SQL Server: TOP 20 or OFFSET/FETCH
-- DISTINCT, aliases, and NULL-safe output
SELECT DISTINCT country,
       COALESCE(nickname, name, 'unknown') AS display_name
FROM customers;

BETWEEN a AND binclusive on both endson timestamps it misses the last instant (see topic 10)
IN (…)matches any listed valueNOT IN (subquery) + one NULL → empty result
LIKE '%x_'% = any run, _ = one charleading % cannot use a normal index
ILIKEcase-insensitive (PostgreSQL)MySQL: LIKE is case-insensitive by collation; or use LOWER()

-- Quoted identifiers: standard SQL uses "..." for column/table names,
-- MySQL uses backticks. (Strings use single quotes in every dialect.)
SELECT "weird col name" FROM t;     -- PostgreSQL: case-sensitive identifier
SELECT `weird col name` FROM t;     -- MySQL: backtick form
Interview trapSQL uses three-valued logic: WHERE age <> 30 silently drops rows where age is NULL, because NULL <> 30 evaluates to UNKNOWN, not true. If you want them, add OR age IS NULL. Likewise WHERE dept NOT IN (SELECT dept FROM t) returns zero rows if the subquery yields a single NULL.
AnalogyNULL is not "zero" or "empty string" — it is "unknown". Asking "is unknown equal to 30?" has no yes/no answer, which is exactly why every comparison with NULL returns UNKNOWN and needs IS NULL.

02Clause Execution Order

You write a query top-down, but the engine evaluates it in a different order. Internalize this once and a dozen interview puzzles ("why can't I use my alias here?") answer themselves.

1FROM→ 2JOIN / ON→ 3WHERE→ 4GROUP BY→ 5HAVING→ 6SELECT→ 7DISTINCT→ 8ORDER BY→ 9LIMIT / OFFSET 
-- Consequence: SELECT aliases do not exist yet in WHERE,
-- but they do exist by the time ORDER BY runs.
SELECT name, salary * 12 AS annual
FROM employees
WHERE salary * 12 > 100000      -- ✗ "annual" is illegal here (step 3 runs before step 6)
ORDER BY annual DESC;           -- ✓ legal here (step 8 runs after step 6)
-- Same logic for aggregates: WHERE filters rows BEFORE grouping,
-- HAVING filters groups AFTER aggregation.
SELECT country, COUNT(*) AS n
FROM customers                  -- step 1: the raw row set
WHERE deleted_at IS NULL        -- step 3: drop rows early (cheap)
GROUP BY country                -- step 4: collapse into groups
HAVING COUNT(*) >= 100          -- step 5: keep only big groups
ORDER BY n DESC;                -- step 8
Why interviewers love thisWindow functions are computed in step 6 (SELECT), so they cannot appear in WHERE or HAVING. The standard fix is "wrap it and filter outside" — a subquery or CTE (topic 06 shows the pattern).
Dialect noteMySQL allows using a SELECT alias inside HAVING and GROUP BY (a non-standard extension). PostgreSQL does not — repeat the expression or use a subquery. Portable SQL repeats the expression.

03Joins

A join combines rows from two tables using a match condition. Learn the four Venn shapes, the ON vs WHERE distinction, and the self join — that covers ~90% of join questions.

-- INNER: only rows with a match on both sides
SELECT o.order_id, c.name
FROM orders o
INNER JOIN customers c ON c.customer_id = o.customer_id;

-- LEFT: every customer, plus their orders when they exist (NULLs otherwise)
SELECT c.name, o.order_id
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id;

-- Anti-join: customers with NO orders at all
SELECT c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.order_id IS NULL;

-- SELF JOIN: one table twice — employees next to their manager
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.employee_id = e.manager_id;

-- CROSS JOIN: every pairing (sizes × colors = catalog grid)
SELECT s.size, c.color
FROM sizes s
CROSS JOIN colors c;
Interview trap · ON vs WHEREFiltering the right-hand table in WHERE quietly demotes a LEFT JOIN to an INNER JOIN:
-- Silently becomes an INNER join: NULL-total rows fail "o.total > 100"
SELECT c.name, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
WHERE o.total > 100;

-- Keep unmatched customers: put the condition in ON instead
SELECT c.name, o.total
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.customer_id
                  AND o.total > 100;
Rule of thumbConditions about the match belong in ON; conditions about the final rows belong in WHERE. For anti-joins prefer NOT EXISTS (topic 05) — it is NULL-safe and reads as the intent.

04GROUP BY & HAVING

Aggregation collapses many rows into one summary row per group. WHERE filters rows before grouping; HAVING filters groups after.

AnalogyGROUP BY is sorting mail into pigeonholes: each letter lands in exactly one box, and at the end each box produces a single summary slip (COUNT, AVG, …). HAVING then decides which boxes to keep.
SELECT country,
       COUNT(*)            AS customers,
       AVG(age)            AS avg_age,
       MIN(signup_date)    AS first_signup
FROM customers
WHERE deleted_at IS NULL
GROUP BY country
HAVING COUNT(*) >= 100
ORDER BY customers DESC;
-- Group by an expression (e.g. monthly totals) — repeat it or use positional 1
SELECT DATE_TRUNC('month', created_at) AS month,
       SUM(total) AS revenue
FROM orders
GROUP BY DATE_TRUNC('month', created_at)   -- MySQL/PG also allow GROUP BY 1
ORDER BY month;
CallCountsNULL handling
COUNT(*)all rows in the groupcounts everything
COUNT(col)rows where col is not NULLignores NULLs
COUNT(DISTINCT col)unique non-NULL valuesignores NULLs
AVG(col) / SUM(col)over non-NULL values onlyNULLs neither counted nor averaged
The iron ruleEvery column in SELECT must be either in GROUP BY or inside an aggregate. SELECT country, city, COUNT(*) … GROUP BY country errors in PostgreSQL; MySQL (with ONLY_FULL_GROUP_BY off) picks a random city — which is a bug, not a feature, and saying exactly that in an interview earns points.

05Subqueries

A query inside a query, like a nested function call. Know the four placements — scalar, derived, correlated, and EXISTS — and when each one is the right tool.

-- 1 · Scalar: returns ONE value, usable anywhere a value is expected
SELECT name, salary
FROM employees
WHERE salary > (SELECT AVG(salary) FROM employees);

-- 2 · Derived table: a whole result set used as a FROM source (needs an alias!)
SELECT dept, avg_sal
FROM (
  SELECT dept, AVG(salary) AS avg_sal
  FROM employees
  GROUP BY dept
) t
WHERE avg_sal > 80000;

-- 3 · Correlated: references the outer row — conceptually runs once PER outer row
SELECT e.name
FROM employees e
WHERE EXISTS (
  SELECT 1
  FROM orders o
  WHERE o.emp_id = e.employee_id      -- ← the correlation
    AND o.total > 1000
);

-- 4 · NOT EXISTS: "has no matching child" — the NULL-safe anti-join
SELECT c.name
FROM customers c
WHERE NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id
);
FormReturnsTypical use
Scalarsingle value> (SELECT AVG(…)) comparisons
Deriveda tablepre-aggregate before joining; needs an alias
Correlatedvalue per outer rowper-row checks; expensive — often rewritable as a JOIN
EXISTStrue/falsesemi-join / anti-join; stops at first match
Interview trapNOT IN with a nullable subquery is a landmine (one NULL → no rows at all). NOT EXISTS and LEFT JOIN … IS NULL both behave correctly; NOT EXISTS states the intent best.
Performance smellA correlated subquery on a big table is O(n²)-ish. If you find one inside a slow query, the usual rewrite is a JOIN onto a pre-aggregated derived table, or a window function.

06Window Functions

The #1 interview topic. GROUP BY collapses rows; a window function adds a summary sticky note to every row without collapsing anything. Same aggregation power, full row detail.

AnalogyPARTITION BY deals the rows into separate hands of cards; ORDER BY sorts each hand; the function then writes a note on every card — its rank, its neighbor, the running total — without merging any cards together.
-- The three rankers — memorize the difference:
--   ROW_NUMBER  1,2,3,4   unique, arbitrary tie-break
--   RANK        1,2,2,4   ties share, then GAP
--   DENSE_RANK  1,2,2,3   ties share, NO gap
SELECT name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) AS rnk,
       DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) AS drnk
FROM employees;
-- LAG / LEAD: peek at the previous / next row — period-over-period change
SELECT day, revenue,
       LAG(revenue)  OVER (ORDER BY day)          AS prev_day,
       revenue - LAG(revenue) OVER (ORDER BY day) AS delta,
       LEAD(revenue) OVER (ORDER BY day)          AS next_day
FROM daily_revenue;
-- Running total and 7-day moving average (frame clause controls the window)
SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day) AS running_total,
       AVG(revenue) OVER (ORDER BY day
                          ROWS BETWEEN 6 PRECEDING AND CURRENT ROW) AS ma7
FROM daily_revenue;
FrameRows in the windowTypical answer
ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROWpartition start → currentrunning total
ROWS BETWEEN 6 PRECEDING AND CURRENT ROWtrailing 7 rowsmoving average
ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWINGcentered 3 rowssmoothing
ROWS BETWEEN UNBOUNDED PRECEDING AND UNBOUNDED FOLLOWINGwhole partitionshare of total
-- NTILE: bucket rows into N roughly equal groups (quartiles, deciles)
SELECT name, salary, NTILE(4) OVER (ORDER BY salary DESC) AS quartile
FROM employees;

-- WINDOW clause: define once, reuse several times
SELECT name, dept, salary,
       RANK() OVER w AS rnk,
       ROUND(salary - AVG(salary) OVER w, 2) AS vs_dept_avg
FROM employees
WINDOW w AS (PARTITION BY dept ORDER BY salary DESC);
-- THE classic: "top 3 per group" — windows can't live in WHERE, so wrap them
WITH ranked AS (
  SELECT name, dept, salary,
         ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn <= 3;
GROUP BYWindow function

See neighbors?noLAG/LEAD, frames
Dialect noteMySQL 8.0+ supports window functions and the WINDOW clause shown above; pre-8.0 MySQL has neither. In SQL Server the same frame syntax works, but the reusable WINDOW clause does not — inline each OVER(…).

07CTEs & Recursion

A CTE (WITH clause) is a named, temporary result set that makes long queries read like a recipe: step 1, step 2, step 3. Recursive CTEs additionally let a step feed into itself — hierarchies and sequence generation.

-- Non-recursive: name each pipeline step
WITH high_value AS (
  SELECT customer_id, SUM(total) AS lifetime
  FROM orders
  GROUP BY customer_id
), recent AS (
  SELECT customer_id, MAX(created_at) AS last_order
  FROM orders
  GROUP BY customer_id
)
SELECT c.name, h.lifetime, r.last_order
FROM customers c
JOIN high_value h ON h.customer_id = c.customer_id
JOIN recent r     ON r.customer_id = c.customer_id
WHERE h.lifetime > 5000;
-- Recursive CTE anatomy: ANCHOR (base case) + RECURSIVE STEP, UNION ALL
WITH RECURSIVE org AS (
  SELECT employee_id, name, manager_id, 1 AS depth          -- anchor: the CEO
  FROM employees
  WHERE manager_id IS NULL
  UNION ALL
  SELECT e.employee_id, e.name, e.manager_id, o.depth + 1   -- step: one level down
  FROM employees e
  JOIN org o ON e.manager_id = o.employee_id
)
SELECT * FROM org ORDER BY depth;
AnalogyThe anchor is the bottom stair; the recursive step is "from wherever you are, take one more stair"; the engine keeps taking stairs until the step returns nothing. Termination must be guaranteed by the data (or an explicit depth guard), or the query loops forever.
Interview trapCyclic data (A manages B, B manages A) loops forever. Guards: a depth < 50 predicate, or a visited-path array in PostgreSQL (ARRAY[employee_id] extended each step and checked with NOT = ANY).
Dialect notePostgreSQL: RECURSIVE keyword optional-ish (required only for recursive CTEs, allowed always). MySQL 8: write WITH RECURSIVE whenever any CTE recurses; the recursion depth cap (cte_max_recursion_depth, default 1000) can be raised per session.

08Set Operations

Joins grow rows sideways (new columns); set operations stack results vertically (new rows). Both inputs need the same number of columns with compatible types.

-- UNION dedupes (implicit DISTINCT = sort/hash cost); UNION ALL keeps everything
SELECT name, 'customer' AS source FROM customers
UNION
SELECT name, 'supplier' AS source FROM suppliers;

SELECT name FROM customers_2024
UNION ALL                       -- the fast default when duplicates don't matter
SELECT name FROM customers_2025;

-- INTERSECT: rows present in both
SELECT email FROM newsletter   INTERSECT   SELECT email FROM purchasers;

-- EXCEPT: rows in the first, not in the second   (Oracle: MINUS)
SELECT email FROM signed_up    EXCEPT      SELECT email FROM showed_up;
RulesDetail
Column countidentical in both inputs
Typespositionally compatible (implicit cast may apply)
Namesoutput takes names from the first SELECT
ORDER BYonly once, at the very end — it applies to the combined result
Interview classic"UNION vs UNION ALL?" — UNION removes duplicates (extra sort/hash), UNION ALL does not. The strong answer adds: dedup only when duplicates are possible and meaningless; default to UNION ALL and dedup explicitly when needed.

10Date & Time

Nearly every analytics question is "grouped by some period of time". The dialects disagree the most here, so anchor on the concepts: extract a part, truncate to a period, do arithmetic, format output.

-- Monthly revenue, last 6 months (PostgreSQL)
SELECT DATE_TRUNC('month', created_at)::date AS month,
       SUM(total) AS revenue
FROM orders
WHERE created_at >= CURRENT_DATE - INTERVAL '6 months'
GROUP BY 1
ORDER BY 1;
-- MySQL version of the same query
SELECT DATE_FORMAT(created_at, '%Y-%m-01') AS month,
       SUM(total) AS revenue
FROM orders
WHERE created_at >= CURDATE() - INTERVAL 6 MONTH
GROUP BY month
ORDER BY month;
Interview trap · BETWEEN on timestampscreated_at BETWEEN '2024-01-01' AND '2024-01-31' drops everything after midnight on the 31st. The robust pattern is a half-open range: created_at >= start AND created_at < end.
Time zonesStore timestamps in UTC (TIMESTAMPTZ in PostgreSQL). Convert only at the edges: created_at AT TIME ZONE 'Asia/Kolkata'. "Why is my daily report shifted by a few hours?" is a timezone question wearing a SQL costume.

11DML & Upserts

Insert, update, delete — plus the interview favorite: "insert if new, update if exists" (upsert). Every engine has its own spelling of upsert; know all three.

-- INSERT: explicit rows, or the result of a SELECT
INSERT INTO customers (name, country) VALUES ('Ada', 'UK'), ('Grace', 'US');

INSERT INTO top_customers (customer_id, plan)
SELECT customer_id, plan FROM staging WHERE lifetime > 5000;

-- UPDATE with a join (PostgreSQL: UPDATE ... FROM)
UPDATE orders o
SET status = 'hold'
FROM customers c
WHERE o.customer_id = c.customer_id
  AND c.country = 'XX';

-- DELETE with a join (PostgreSQL: DELETE ... USING)
DELETE FROM orders
USING customers c
WHERE orders.customer_id = c.customer_id
  AND c.banned = TRUE;

-- PostgreSQL: get data back out of the write (MySQL: use LAST_INSERT_ID())
INSERT INTO shipments (order_id) VALUES (42)
RETURNING shipment_id, created_at;
-- UPSERT · PostgreSQL — ON CONFLICT
INSERT INTO counters (counter_key, hits) VALUES ('login', 1)
ON CONFLICT (counter_key) DO UPDATE
SET hits = counters.hits + EXCLUDED.hits;   -- EXCLUDED = the row you tried to insert
-- UPSERT · MySQL — ON DUPLICATE KEY UPDATE (no SET keyword here!)
INSERT INTO counters (counter_key, hits) VALUES ('login', 1)
ON DUPLICATE KEY UPDATE hits = hits + VALUES(hits);
-- MySQL 8.0.20+ prefers a row alias over VALUES():
-- INSERT INTO counters (counter_key, hits) VALUES ('login', 1) AS new
-- ON DUPLICATE KEY UPDATE hits = hits + new.hits;
-- UPSERT · SQL Server / Oracle — MERGE
MERGE INTO counters t
USING (VALUES ('login', 1)) AS s (counter_key, hits)
  ON t.counter_key = s.counter_key
WHEN MATCHED THEN UPDATE SET hits = t.hits + s.hits
WHEN NOT MATCHED THEN INSERT (counter_key, hits)
  VALUES (s.counter_key, s.hits);
DELETE vs TRUNCATEDELETETRUNCATE
Rowsany subset (WHERE)all rows only
Speedrow by row, loggednear-instant (deallocates pages)
Triggers / RETURNINGfires row triggersskipped
Resets identity?noyes (by default)
Interview trap"TRUNCATE is DDL, not DML" — in PostgreSQL it is transactional (rollback works), in MySQL it causes an implicit commit. Mentioning that nuance is a senior signal.

12DDL, Constraints & Indexes

Schema design questions test whether data integrity lives in the database or in hope. Constraints are the answer; indexes are the speed.

CREATE TABLE orders (
  order_id    BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY,   -- PG; MySQL: BIGINT AUTO_INCREMENT
  customer_id BIGINT NOT NULL
              REFERENCES customers (customer_id) ON DELETE CASCADE,
  status      VARCHAR(20)  NOT NULL DEFAULT 'pending',
  total       NUMERIC(10,2) NOT NULL CHECK (total >= 0),
  created_at  TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
  UNIQUE (customer_id, created_at)
);

ALTER TABLE orders ADD COLUMN coupon_code VARCHAR(20);
ALTER TABLE orders ADD CONSTRAINT fk_reviews
  FOREIGN KEY (customer_id) REFERENCES customers (customer_id);
ALTER TABLE orders RENAME COLUMN total TO amount;     -- PG (12+ online) / MySQL 8
ALTER TABLE orders DROP COLUMN coupon_code;

-- Indexes
CREATE INDEX idx_orders_customer ON orders (customer_id, created_at DESC);
CREATE UNIQUE INDEX idx_users_email_active
  ON users (email) WHERE deleted_at IS NULL;          -- partial index (PG)
CREATE INDEX idx_orders_cover ON orders (customer_id) INCLUDE (status);  -- covering (PG 11+)
ConstraintGuaranteesInterview line
PRIMARY KEYunique + not null identity of the rowone per table, backed by an index
FOREIGN KEYchild rows point at real parentsdefine the delete behavior: CASCADE / SET NULL / RESTRICT
UNIQUEno duplicate valuesallows multiple NULLs in PG; one NULL in MySQL (InnoDB treats NULLs as distinct)
CHECKrow satisfies a boolean ruleprice >= 0 belongs here, not in app code alone
NOT NULL / DEFAULTpresence + fallbackdefaults are evaluated at insert time
Composite index ruleAn index on (a, b, c) serves filters on a, a+b, a+b+c — the leftmost prefix rule. It cannot skip a to use b. Order columns: equality predicates first, range/sort column last.
What kills an indexA function or cast on the indexed column (WHERE UPPER(name) = …, WHERE created_at::date = …), a leading-wildcard LIKE '%son', and mismatched types (WHERE phone = 5551234 against a VARCHAR column) all prevent B-tree use. Fix pattern: make predicates sargable — see topic 14.

13Ten Classic Interview Patterns

Learn these ten shapes and most live coding questions become remixes. Each snippet is deliberately minimal — extend, don't memorize.

13.1Second-highest salary

-- Approach A: two aggregates     B: skip one row     C: rank and filter
SELECT MAX(salary) FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);

SELECT DISTINCT salary FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;                        -- SQL Server: OFFSET 1 ROWS FETCH NEXT 1 ROWS ONLY

SELECT DISTINCT salary,
       DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
FROM employees;                          -- then filter rnk = 2 (NULL-proof, extensible to Nth)

13.2Find & delete duplicates

-- Find them
SELECT email, COUNT(*) FROM users GROUP BY email HAVING COUNT(*) > 1;

-- Delete the extras, keeping the lowest id per email (PostgreSQL)
WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
  FROM users
)
DELETE FROM users USING ranked
WHERE users.id = ranked.id AND ranked.rn > 1;

13.3Top-N per group

WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) AS rn
  FROM employees
)
SELECT * FROM ranked WHERE rn <= 3;      -- ties handled? use RANK/DENSE_RANK

13.4Running total

SELECT day, revenue,
       SUM(revenue) OVER (ORDER BY day) AS running_total
FROM daily_revenue;

13.5Period-over-period growth

SELECT month, revenue,
       LAG(revenue) OVER (ORDER BY month) AS prev,
       ROUND(100.0 * (revenue - LAG(revenue) OVER (ORDER BY month))
             / LAG(revenue) OVER (ORDER BY month), 1) AS growth_pct
FROM monthly_revenue;

13.6Pivot: rows to columns

SELECT customer_id,
       SUM(CASE WHEN month = 'jan' THEN revenue ELSE 0 END) AS jan,
       SUM(CASE WHEN month = 'feb' THEN revenue ELSE 0 END) AS feb,
       SUM(CASE WHEN month = 'mar' THEN revenue ELSE 0 END) AS mar
FROM sales
GROUP BY customer_id;

13.7Anti-join: no matching child

SELECT c.name
FROM customers c
WHERE NOT EXISTS (SELECT 1 FROM orders o WHERE o.customer_id = c.customer_id);
-- equivalent shape: LEFT JOIN ... WHERE o.order_id IS NULL

13.8Consecutive-day streaks

-- date minus dense row number is constant inside a streak (see 15.1)
WITH days AS (
  SELECT DISTINCT user_id, login_date::date AS d
  FROM logins
), stamped AS (
  SELECT user_id, d,
         d - ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY d) AS grp
  FROM days
)
SELECT user_id, MIN(d) AS streak_start, MAX(d) AS streak_end, COUNT(*) AS days
FROM stamped
GROUP BY user_id, grp
ORDER BY user_id, streak_start;

13.9Bucketing into bands

SELECT CASE WHEN age < 18 THEN 'under 18'
            WHEN age < 35 THEN '18-34'
            WHEN age < 60 THEN '35-59'
            ELSE '60+' END AS age_band,
       COUNT(*) AS users
FROM users
GROUP BY 1
ORDER BY 1;

13.10Latest row per entity

SELECT * FROM (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) AS rn
  FROM events
) t
WHERE rn = 1;                            -- full strategies in 15.3

14Performance & EXPLAIN

"This query is slow — how do you fix it?" is really two questions: can you read the plan, and do you know what makes predicates index-friendly.

-- EXPLAIN shows the plan; ANALYZE actually executes and adds real timings
EXPLAIN ANALYZE
SELECT order_id, total
FROM orders
WHERE customer_id = 42 AND status = 'shipped';

-- What to look for:
--   Seq Scan on a big table that has a useful index  → index missing / not usable
--   rows=1000 estimated vs rows=87 actual            → stale statistics → run ANALYZE
--   Nested Loop over 1M rows                         → join strategy mismatch
--   Sort node with no index supporting ORDER BY      → consider index on sort keys
Not sargable (index dies)Sargable (index works)
WHERE UPPER(name) = 'ADA'store normalized column, or expression index on UPPER(name)
WHERE created_at::date = '2024-01-01'WHERE created_at >= '2024-01-01' AND created_at < '2024-01-02'
WHERE name LIKE '%son'trigram/pg_trgm index, or reverse-store + 'nos%'
WHERE phone = 5551234 (int vs VARCHAR col)WHERE phone = '5551234' (no implicit cast)
WHERE YEAR(d) = 2024WHERE d >= '2024-01-01' AND d < '2025-01-01'
Fast checklist1) index the join + filter columns  2) keep predicates sargable  3) SELECT named columns, not * (enables covering indexes, less I/O)  4) prefer EXISTS over IN for big nullable subqueries  5) UNION ALL unless dedup is required  6) batch the app's N+1 queries into one join  7) refresh statistics after bulk loads.
AnalogyAn index is a book's back-of-book index: perfect for "find all pages mentioning X", useless for "find pages where chapter starts with X" if the index only stores full titles. Wrapping the column in a function is exactly that mismatch.

15Advanced Patterns

The "senior-sounding" questions: gaps & islands, sessionization, deduplication, percentiles, SCD Type 2, cohorts, unpivoting, date spines, lateral joins, and multi-grain rollups. They mostly reuse one skeleton: LAG to flag a boundary, SUM over the flag to number groups.

15.1Gaps & Islands

Group consecutive things (streak of daily logins, contiguous seat rows, uninterrupted sensor readings) into islands. Flag where a new island starts, then turn the flag into an island id with a running sum.

-- Islands of consecutive login days, per user
WITH flagged AS (
  SELECT user_id, login_date::date AS d,
         CASE WHEN login_date::date - LAG(login_date::date) OVER w = 1
              THEN 0 ELSE 1 END AS new_island
  FROM (SELECT DISTINCT user_id, login_date FROM logins) l
  WINDOW w AS (PARTITION BY user_id ORDER BY login_date::date)
),
grouped AS (
  SELECT *, SUM(new_island) OVER (PARTITION BY user_id ORDER BY d) AS island_id
  FROM flagged
)
SELECT user_id,
       MIN(d)    AS island_start,
       MAX(d)    AS island_end,
       COUNT(*)  AS days
FROM grouped
GROUP BY user_id, island_id
ORDER BY user_id, island_start;
Dialect note (corrected)MySQL 8.0+ supports window functions and the WINDOW w AS (…) clause — keep this code nearly as-is and only change the date math: login_date - INTERVAL 1 DAY instead of ::date - 1. (It's pre-8.0 MySQL that has no window functions at all — there you'd emulate with self-joins or user variables.)

15.2Sessionization

The 30-minute rule: a new session starts when the gap since the previous event exceeds 30 minutes. Same skeleton as 15.1 — learn one, get both.

WITH steps AS (
  SELECT user_id, login_at,
         LAG(login_at) OVER w AS prev_at
  FROM logins
  WINDOW w AS (PARTITION BY user_id ORDER BY login_at)
),
flagged AS (
  SELECT *,
         CASE WHEN prev_at IS NULL
               OR login_at - prev_at > INTERVAL '30 minutes'
              THEN 1 ELSE 0 END AS new_session
  FROM steps
),
numbered AS (
  SELECT *, SUM(new_session) OVER (PARTITION BY user_id ORDER BY login_at) AS session_no
  FROM flagged
)
SELECT user_id, session_no,
       MIN(login_at) AS session_start,
       MAX(login_at) AS session_end,
       COUNT(*)      AS events
FROM numbered
GROUP BY user_id, session_no
ORDER BY user_id, session_start;
MySQL 8.0+Works with the same WINDOW clause; write the gap test as TIMESTAMPDIFF(MINUTE, prev_at, login_at) > 30.

15.3Deduplication — five strategies

#StrategyDialectsTiesBest for
1ROW_NUMBER() = 1everywhere (8.0+ for MySQL)arbitrary pickkeep latest per natural key
2QUALIFYBigQuery, Snowflake, DuckDB, Teradataarbitrary pickone-liner, no CTE
3DISTINCT ONPostgreSQL onlyarbitrary firstquick PG one-liner
4self-join / anti-join deleteeverywhere—physically removing rows
5RANK() = 1everywhere (8.0+ for MySQL)keeps all tieswhen ties must survive
-- 1 · ROW_NUMBER: keep the latest row per email
WITH ranked AS (
  SELECT *, ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) AS rn
  FROM users
)
SELECT * FROM ranked WHERE rn = 1;

-- 1b · and physically delete the extras (PostgreSQL)
WITH ranked AS (
  SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) AS rn
  FROM users
)
DELETE FROM users USING ranked
WHERE users.id = ranked.id AND ranked.rn > 1;

-- 2 · QUALIFY: filter windows directly, no CTE needed
SELECT * FROM users
QUALIFY ROW_NUMBER() OVER (PARTITION BY email ORDER BY updated_at DESC) = 1;

-- 3 · DISTINCT ON: PostgreSQL keeps the first row per group
SELECT DISTINCT ON (email) * FROM users ORDER BY email, updated_at DESC;

-- 5 · RANK keeps ties: two players tied at the top both survive
WITH ranked AS (
  SELECT *, RANK() OVER (PARTITION BY email ORDER BY score DESC) AS rnk
  FROM players
)
SELECT * FROM ranked WHERE rnk = 1;

15.4Percentiles & medians

PERCENTILE_CONT interpolates between neighboring values (can return a value nobody has); PERCENTILE_DISC returns an actual stored value. Median = 50th percentile.

-- PostgreSQL / Oracle / Snowflake
SELECT PERCENTILE_CONT(0.5) WITHIN GROUP (ORDER BY salary) AS median_salary,
       PERCENTILE_DISC(0.9) WITHIN GROUP (ORDER BY salary) AS p90_salary
FROM employees;
-- MySQL 8 has no PERCENTILE_* — emulate the median with ROW_NUMBER + COUNT
WITH r AS (
  SELECT salary,
         ROW_NUMBER() OVER (ORDER BY salary) AS rn,
         COUNT(*)     OVER ()                AS n
  FROM employees
)
SELECT AVG(salary) AS median
FROM r
WHERE rn IN (FLOOR((n + 1) / 2), CEIL((n + 1) / 2));

15.5SCD Type 2 (history tracking)

Slowly Changing Dimension Type 2 keeps a row per version: valid_from, valid_to, current flag. Build it from an event log in three mini-steps.

WITH flagged AS (
  SELECT customer_id, city, updated_at,
         CASE WHEN city = LAG(city) OVER (PARTITION BY customer_id ORDER BY updated_at)
              THEN 0 ELSE 1 END AS is_change
  FROM customers_raw
),
versioned AS (
  SELECT *, SUM(is_change) OVER (PARTITION BY customer_id ORDER BY updated_at) AS version_no
  FROM flagged
)
SELECT customer_id, city, version_no,
       MIN(updated_at) AS valid_from,
       LEAD(MIN(updated_at)) OVER (PARTITION BY customer_id ORDER BY MIN(updated_at)) AS valid_to
FROM versioned
GROUP BY customer_id, version_no, city;
Interview framing"Type 1 overwrites (no history), Type 2 adds a new row per change, Type 3 keeps a limited previous column. Type 2 is the default for analytics because it answers point-in-time questions."

15.6Cohort retention

WITH first_seen AS (
  SELECT user_id, DATE_TRUNC('month', MIN(visit_date))::date AS cohort
  FROM visits
  GROUP BY user_id
),
tagged AS (
  SELECT f.cohort, v.user_id,
         EXTRACT(YEAR  FROM AGE(v.visit_date, f.cohort)) * 12
       + EXTRACT(MONTH FROM AGE(v.visit_date, f.cohort))  AS months_since
  FROM first_seen f
  JOIN visits v USING (user_id)
)
SELECT cohort,
       COUNT(DISTINCT user_id) FILTER (WHERE months_since = 0) AS m0,
       COUNT(DISTINCT user_id) FILTER (WHERE months_since = 1) AS m1,
       COUNT(DISTINCT user_id) FILTER (WHERE months_since = 2) AS m2,
       COUNT(DISTINCT user_id) FILTER (WHERE months_since = 3) AS m3
FROM tagged
GROUP BY cohort
ORDER BY cohort;
Portable versionFILTER is PostgreSQL/SQLite; elsewhere use COUNT(DISTINCT CASE WHEN months_since = 1 THEN user_id END). Divide each mN by m0 to get retention percentages.

15.7Unpivot: columns to rows

-- Portable: UNION ALL over the wide columns
SELECT id, 'jan' AS month, jan AS revenue FROM monthly_revenue
UNION ALL SELECT id, 'feb', feb FROM monthly_revenue
UNION ALL SELECT id, 'mar', mar FROM monthly_revenue;

-- Dedicated syntax: SQL Server / Oracle
SELECT id, month_col, revenue
FROM monthly_revenue
UNPIVOT (revenue FOR month_col IN (jan, feb, mar)) u;

15.8Date spine (fill the calendar gaps)

-- PostgreSQL: no recursion needed
SELECT generate_series('2024-01-01'::date,
                       '2024-12-31'::date,
                       INTERVAL '1 day')::date AS d;
-- MySQL 8: recursive CTE. MySQL has no typed DATE literal (that's
-- PostgreSQL/Oracle syntax) — use CAST('...' AS DATE) or a plain string.
SET SESSION cte_max_recursion_depth = 4000;   -- default 1000 covers ~1 year, raise for longer spines
WITH RECURSIVE calendar AS (
  SELECT CAST('2024-01-01' AS DATE) AS d
  UNION ALL
  SELECT d + INTERVAL 1 DAY
  FROM calendar
  WHERE d < '2024-12-31'                     -- plain string literal: implicit cast
)
SELECT d FROM calendar;
-- Spine LEFT JOIN facts: days with zero sales still appear
SELECT c.d AS day, COALESCE(SUM(o.total), 0) AS revenue
FROM (SELECT generate_series('2024-01-01'::date,
                             '2024-01-31'::date,
                             INTERVAL '1 day')::date AS d) c
LEFT JOIN orders o ON o.created_at::date = c.d
GROUP BY c.d
ORDER BY c.d;

15.9LATERAL / OUTER APPLY

A lateral join lets the right side reference columns of each left row — a correlated subquery that can also ORDER BY ... LIMIT. The clean answer to "top 3 orders per customer" in one pass.

-- PostgreSQL / MySQL 8+: LATERAL
SELECT c.name, top3.*
FROM customers c
CROSS JOIN LATERAL (
  SELECT o.order_id, o.total
  FROM orders o
  WHERE o.customer_id = c.customer_id
  ORDER BY o.total DESC
  LIMIT 3
) top3;

-- SQL Server: CROSS APPLY (inner) / OUTER APPLY (left)
SELECT c.name, t.*
FROM customers c
OUTER APPLY (
  SELECT TOP 3 o.order_id, o.total
  FROM orders o
  WHERE o.customer_id = c.customer_id
  ORDER BY o.total DESC
) t;

-- PostgreSQL left-join flavor: keep customers with zero orders too
SELECT c.name, top3.*
FROM customers c
LEFT JOIN LATERAL (
  SELECT o.order_id, o.total FROM orders o
  WHERE o.customer_id = c.customer_id
  ORDER BY o.total DESC LIMIT 3
) top3 ON TRUE;

15.10GROUPING SETS / ROLLUP / CUBE

Multiple grain levels in one scan: per (region, brand), per region, per brand, and grand total — without four queries.

SELECT region, brand, SUM(sales) AS total
FROM sales_facts
GROUP BY GROUPING SETS ((region, brand), (region), (brand), ());

-- Shorthands:
--   ROLLUP(region, brand) = GROUPING SETS ((region,brand), (region), ())
--   CUBE(region, brand)   = GROUPING SETS ((region,brand), (region), (brand), ())

-- Subtotal rows show NULLs for the rolled columns — tell them apart
-- from real NULLs with GROUPING(): 1 = this column was rolled up
SELECT GROUPING(region) AS r_rollup,
       GROUPING(brand)  AS b_rollup,
       region, brand, SUM(sales)
FROM sales_facts
GROUP BY GROUPING SETS ((region, brand), (region), ());
Interview trap"Why not just UNION the three GROUP BY queries?" — correctness is the same, but GROUPING SETS scans the base table once instead of three times, and GROUPING() disambiguates subtotal NULLs from data NULLs — a UNION can't.

16ACID & Normalization

The theory round. Transactions, the four guarantees, isolation levels versus read anomalies, and normal forms — short answers, precise wording.

16.1Transactions

-- All-or-nothing money move
BEGIN;                                       -- START TRANSACTION
UPDATE accounts SET balance = balance - 100 WHERE account_id = 1;
UPDATE accounts SET balance = balance + 100 WHERE account_id = 2;
COMMIT;                                      -- or ROLLBACK: undo both legs

-- Partial undo inside a longer transaction
SAVEPOINT before_risky;
DELETE FROM orders WHERE status = 'test';
ROLLBACK TO SAVEPOINT before_risky;          -- undo the delete, keep earlier work
RELEASE SAVEPOINT before_risky;

-- Pin the isolation level for this transaction
SET TRANSACTION ISOLATION LEVEL REPEATABLE READ;
ACIDGuaranteeInterview one-liner
Atomicityall statements apply or none do"the transfer debits and credits together or not at all" (undo log)
Consistencyconstraints hold before and after"the database never accepts a state that violates its own rules"
Isolationconcurrent transactions don't see half-done work"implemented with locking and/or MVCC snapshots"
Durabilitycommitted data survives a crash"the write-ahead log is flushed before the commit is acknowledged"

16.3Normal forms in one table

FormRuleMicro-example (violation → fix)
1NFatomic values, no repeating groupsphones = "555-0100, 555-0101" → one row per phone
2NFno partial dependency on part of a composite keykey (order_id, product_id) carrying product_name → move name to products

The pragmatic answer"Normalize to 3NF for OLTP; denormalize deliberately for analytics." Interviewers want the trade-off, not dogma.
Star vs snowflakeA star schema is one fact table (orders: foreign keys + measures) surrounded by denormalized dimension tables — fewer joins, fast BI queries. The snowflake normalizes dimensions further (dim_city → dim_region): less redundancy, more joins. Stars dominate dashboards; snowflakes save storage.
